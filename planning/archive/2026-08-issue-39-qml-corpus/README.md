# QML corpus hosted in gq (#39) — complete

Shipped in **v0.4.0**. All phases landed; `planning/active/` freed 2026-08-24.

## Outcome

`inst/styles/` now carries 60 QGIS-native style files — 50 shared vector styles,
3 per-template overrides, 1 raster, 6 services — served by
`gq_style_qml(layer_key, template = NULL)` and regenerated by
`data-raw/styles_vendor.R`. The registry stays the cross-backend abstraction for
tmap and mapgl; the corpus is the lossless form for anything rendering back to
QGIS.

## The finding that reshaped the work

The issue's premise died before implementation started. It was filed 2026-08-03
arguing the QML lived "in whichever field project someone last styled, not in a
versioned package"; rfp#174 Phase A landed a committed store in rfp on
2026-08-23. So the work was never "build the corpus" — it was "decide where it
lives", which was put to the user as an explicit scoping question rather than
assumed. Answer: host it in gq, rfp keeps its copy until rfp#188 repoints its
builder.

Two design points came from measuring rather than reading:

- **Vendor through `index.csv`, never by globbing.** `vector/osm.trail.qml` is
  tracked upstream with no index row — the gq#41 trail donor, superseded by the
  generated `trails.qml`. rfp's own guard walks index → file only, so it cannot
  see a stray. Filed as rfp#187; carried here as a declared exception with a
  reason, to be dropped when that lands.
- **`(layer_key, template)` has zero collisions** across all 53 index rows, so
  no styleName-style discriminator was needed. Worth checking because rfp's
  store is keyed per QGIS *layer*, not per table — `bcfishpass.streams_vw` backs
  four differently-styled layers.

## Two guards proven against both answers, not just the passing one

- The vendoring script's orphan check **aborted on real data** before the
  exception was declared, and passed after.
- The byte-identity test **failed first**, reporting 59 false drifts, because it
  compared against the *installed* rfp 0.25.1 (3 raster QMLs, no store) rather
  than the 0.30.1 checkout. That is the installed-vs-source trap
  `reg_extract_themes.R` already documents. It now takes `RFP_STYLES_DIR` first
  and skips when upstream predates rfp#174 — honest when it cannot compare,
  strict when it can.

## Verification

391 tests pass, 0 fail. `R CMD check` adds no errors, warnings or notes over
main (2 warnings and 2 notes are pre-existing, confirmed against main rather
than assumed). Tarball verified to ship the corpus and its index with no
`planning/` or `CLAUDE.md` leak. Vendoring verified idempotent by tree digest.

## Found, not fixed

on main as well. Unrelated to this work; both are harmless but are noise in
every install.

## Second round — the Plan review landed after the PR

The concurrent Plan agent returned once #50 was already open, so it reviewed
landed code rather than a plan. That is the better version of a late review:
7 of its 12 findings were real and 3 were disproved by a probe.

**Disproved.** The slugifier guard was said to be unsatisfiable on NA rows — the
landed test already scoped past them and passed. `LazyData: true` was said to
have no `data/` — there are 23 files in it. And the concern that
`rfp_styles_apply()` wants QML *text* is wrong: it reads the path itself, so a
bare path is the right return.

**Acted on.** `raster/`/`services/` were being globbed, and two files were
getting through that the slug-stability check could never catch —
`dem_hillshade` and `dem_turbo`, which back `rfp_raster_styles()` and carry a
renderer/stretch dimension gq vendors none of. They now resolve against rfp's
template roster, which drops both and also recovers the display names for the
other seven. That, in turn, let two guards get stronger:

- the slugifier guard covers **every** row rather than the 53 named ones
- the structural guard asserts the positional invariant rfp actually uses —
  the style block starts at `<flags>` — which the previous absence-only check
  could not do while those two sidecars were present, and which would not have
  caught an rfp#130-class leak

Also fixed: an unknown `template` silently returned the shared style, on exactly
the 3 layers where an override exists *because* the shared one is wrong for that
template; and the cross-kind collision check ran on the vector index rather than
the assembled corpus.

**The finding that mattered most** was that the repo had no `R-CMD-check`
workflow at all — pkgdown was the only CI, and it runs no tests. Every guard
here lived on one machine. `.github/workflows/R-CMD-check.yaml` now runs them on
every PR, which is what makes the rest durable.
