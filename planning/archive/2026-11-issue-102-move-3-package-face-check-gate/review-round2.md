- **[severity: bug]** R/data.R:73-74 (and man/bittner_pscis.Rd; the same claim in the vignette comment at vignettes/gq-intro.Rmd:57) — "Fish passage assessments from PSCIS within 2 km of the Bittner Creek watershed". The query selects `ST_Intersects(a.geom, ST_Expand(ws.geom, 2000))`, and `ST_Expand` grows the watershed's **bounding box**, not the polygon. Measured on the bundled data in BC Albers: two of the 23 assessments are 2,172 m and 2,529 m from the watershed, so the sentence written on this branch is false for the dataset it documents. Either say "within 2 km of the watershed's bounding box" or select with `ST_DWithin(a.geom, ws.geom, 2000)`.
  - **Rule:** none

- **[severity: fragile]** data-raw/bittner_creek.R:49 with vignettes/gq-intro.Rmd:122 — the vignette dropped `st_make_valid()` from the mask on the grounds that the bundled boundary is now valid, but the script still produces it with `ST_Simplify(geom, 50)`, which does not preserve topology and asserts nothing about the result. The previous pull made exactly that kind of polygon (old `bittner_wsd`: "Loop 0: Edge 145 crosses edge 148", 269 vertices); this one happens to be valid. The next re-pull can silently commit an invalid boundary again, and the vignette's `st_difference(bb_box, st_geometry(bittner_wsd))` under `sf_use_s2(FALSE)` would then fail with a GEOS TopologyException at the pkgdown build, far from the script that caused it. `ST_SimplifyPreserveTopology`, or a `stopifnot(all(st_is_valid(bittner_wsd)))` before `use_data()`, closes it.
  - **Rule:** none
